# React ↔ Rust bridge, version 2 (FlowTranslate 0.4.0)

> La DA Îlot ([docs/DA-PLAN.md](DA-PLAN.md)) étend ce contrat sur la branche da-ilot ; les sections concernées sont mises à jour lot par lot.

## Actions, instructions and the language in the prompt (0.3.0 → 0.4.0)

The current `Settings` replaces the legacy `shortcut` field with `actions: ActionDefinition[]`, `shortcutBindings: ShortcutBinding[]`, and `defaultActionId: string`. `ActionDefinition` is `{id, name, promptTemplate}`; `ShortcutBinding` is `{id, shortcut, actionId, outputMode: 'display'|'replace', enabled}`. `src/types.ts` is authoritative for the current contract.

Each native capture includes `execution: {actionId, actionName, outputMode, mode}` (no `targetLanguage` since 0.4.0: the language lives in the instruction). Rust snapshots the corresponding action, prompt and profiles at capture time; the frontend sends `actionId` in `TranslationRequest`, never a prompt. Initial mode and action must match the capture. A comparison/retry may change the profile, but cannot perform another automatic replacement.

`result-delivery` emits `{requestId, status: 'applied'|'fallback', confirmed: boolean, message}` (0.4.0). Stale IDs and closed overlays ignore it. As soon as a « replace » request completes, Rust claims delivery once, revalidates the native target and pastes under the session lock (`capture::paste`, Ctrl+V into the original selection, clipboard restored); `confirmed` says whether the field was read back with the result (bonus proof, never a condition). Before it, the frontend keeps the pill alone; on `applied` the pill shows a check for 900 ms then calls `dismiss_overlay`; on `fallback` the glass opens with the result, the message and Copier; without any report three seconds after `done` the frontend treats it as `fallback`. (The Îlot's journey shows the same outcomes on its own surface instead: « Îlot: the result and the errors on the surface ».) Cancelling even a completed request revokes a pending delivery. Failure leaves the result in the bubble. `capture-target` cannot reactivate replacement after a successful automatic write.

Settings persist through a serialized save queue in React and a mutex in Rust. Registration and persistence errors roll back newly registered shortcuts. Existing API keys remain DPAPI-encrypted. Legacy settings retain their shortcut and profiles; newly reserved legacy shortcuts are disabled, not discarded. Since 0.4.0 a prompt is the instruction alone (1 to 8,000 Unicode characters, no NUL, no variable): Rust sends it as the `system` message and the captured text as the `user` message, so the text is never substituted into the instruction. 0.3.0 templates are migrated on load: `{{targetLanguage}}` becomes `French`/`English` from the former « Langue cible » setting, `{{text}}` and its line are dropped; `defaultActionId` falls back to the first action when its id is gone (`translate` → `translate-fr`).

The settings window is now user-resizable with a dedicated scroll viewport. `resize_settings` was removed; corner dragging calls Tauri `startResizeDragging('SouthEast')`, permitted only for the settings window. Native minimum dimensions are 460 × 420 logical pixels.

Rust structs serialize camelCase. Rust command names are snake_case; invoke arguments use camelCase. Strings returned as errors must be user-readable French and contain no payload or credentials. Since lot 10 of docs/DA-PLAN.md every failure that reaches the frontend as data also carries a code (`ErrorCode`, see « Îlot: error codes »), translated by the frontend into English or French; the French string stays for the v4 journey. The absence of content and secrets in errors remains the rule.

## Îlot: the menu, its keyboard and its focus (uiVersion `ilot`, lot 3)

Only with the hidden `uiVersion: 'ilot'`; in `v4` nothing below changes the old path.

- **Menu capture.** A press of an enabled binding with `kind: 'menu'` captures as before but carries `menu: {lastActionId: string|null}` and **no** `execution`. Rust keeps, for that capture only, a snapshot of the settings at the press and the source window; the frontend shows the menu and does not call `translate` yet. A press while one of our windows (overlay, halo, settings) is in front never takes it as the source: nothing is captured.
- **Choice.** `choose_action({captureId, actionId, instruction?}) -> ExecutionInfo`, once per menu capture (a second call, a stale id, a closed or closing overlay, a direct capture: French error). `actionId` is a saved action of the snapshot, or `'instruction'` with `instruction` (1 to 1,000 Unicode characters after trim, no NUL): Rust builds an ephemeral action « Instruction » whose system prompt is a short rewrite template (follow the user's instruction, keep language, meaning, names and facts unless told otherwise) + the instruction + the usual output rules. The output mode is always `replace`. Rust then sets `capture.execution`, closes the menu scope, makes the overlay non-activatable and, if the overlay holds the foreground, gives it back to the source at once. The frontend then calls `translate` exactly as for a direct capture, with `actionId` = the returned `execution.actionId` (`'instruction'` for a free instruction: the instruction itself never travels again, it stays frozen in Rust). `translate` on a menu capture before its choice is refused (« Choisissez d’abord une action dans le menu. »). The instruction is never logged, stored or saved as an action.
- **Keyboard.** `focus_overlay() -> boolean`: the menu calls it once when it appears. Rust waits (off the main thread, ≤ 900 ms) until the overlay is shown, activates it and answers `true` only if the overlay really holds the foreground afterwards (polled ≤ 40 ms; Windows may refuse the switch). A menu already chosen (a double press can choose before the Îlot shows) is never activated: `false` at once, and a choice that lands during the activation gives the foreground back to the source once the chord is released (review of da-ilot, n°3). With `true` the WebView owns the keyboard: Enter, letters, Tab, arrows, digits, Space and a real `<input>` for the free instruction (AZERTY, dead keys, IME), Escape included (the native hook passes every key while the menu is open and the overlay in front). With `false` the source keeps the foreground and the low-level hook forwards, only while the menu is open and the source in front, the menu keys as `menu-key` and swallows them: Enter, Escape, Tab (with `shiftKey`), arrows, the physical digits 1–6 (row or keypad, so AZERTY needs no Shift), and letters without any modifier read through the source's active layout (ToUnicodeEx, no keyboard state change). Never a chord (Ctrl, Alt or Win held), never Space: no free instruction in that mode. Known limit (measured 2026-09-24): Win11 Notepad gives its keyboard focus to its XAML menu bar on any Alt release it receives (masking keys such as `vkE8` do not prevent it); with the overlay in front the release never reaches it, but in the fallback it does, so the revalidation refuses the paste (nothing is written) and Escape leaves Notepad's focus on its menu bar. The 0.4 direct path meets the same release (the overlay never takes the foreground there): a direct « replace » in that Notepad is refused the same way, with a plain direct binding as with a `menu` binding under `v4`.
- **Escape.** In the focused menu the WebView handles Escape (the Îlot of lot 7 first goes back a level, from the grid or the field to its compact state, then closes; forwarded as `menu-key`, the same table applies). `dismiss_overlay` gives the foreground back to the source when the overlay holds it, then closes as before; nothing is pasted.
- **Keys typed during the capture** (review of da-ilot, n°4 and n°7). A `menu` binding opens the menu's scope at its press, before the capture is taken (a synthetic copy first waits for the chord's release), unless one of our windows is in front. The menu keys typed in the source meanwhile never reach it: Rust holds them and emits them as `menu-key`, in order, right after the `capture` event, with the new capture id. Without a capture (nothing selected, an error) they are dropped, never replayed in the source, and the scope goes back to what is still shown: the previous menu's, the glass's Escape scope, or none.
- **Leaving the menu** (review of da-ilot, n°2 and n°6). Once the overlay has held the foreground for a menu (`focus_overlay` answered `true`, or the hook saw it in front), the hook never takes a key from the source again for that menu: the fallback only serves a menu whose activation was refused. If the user then goes back to the source (a click in his document) or to another application while the menu still waits, Rust closes it as `dismiss_overlay` would (scope closed, Îlot hidden, nothing pasted), within one 35 ms watcher tick. A menu whose selection the watcher drops (window moved or left, selection changed or collapsed) closes the same way instead of receiving `target-invalidated`, and `choose_action` refuses it (« La sélection a changé; le menu est fermé. »). A menu already chosen is never closed by these rules.
- **After the choice.** The overlay carries `WS_EX_NOACTIVATE` and `silent_frame_proc` answers `MA_NOACTIVATE` to `WM_MOUSEACTIVATE`, so a click on the pill (Undo later) never takes the focus from the source; the hit tester keeps the bit through its style rewrites. Lifted at the next capture. A direct `display` binding keeps the old behaviour.
- **Automatic paste.** Like `replace_result`: if one of our windows is in front, Rust reactivates the source and revalidates the target after that (`capture::paste(..., reactivate=true)`, `validate_target` after the reactivation, never before); if another application is in front, it refuses (« La fenêtre source a changé; remplacement refusé. ») and the result stays in the glass.
- **Test switch.** With `FLOWTRANSLATE_CDP_URL` set (WebView2 probe only), `FLOWTRANSLATE_REFUSE_FOCUS` makes `focus_overlay` answer `false` without activating, to exercise the fallback on a real desktop.
- **Frontend.** The Îlot of lot 7 (`src/menu/IlotStage.tsx`, rendered by `GlassSession` while a menu capture's form is pending) drives this contract since 2026-09-24; the provisional `NativeMenuProbe` is gone. `focus_overlay` is called once per menu capture when its stage mounts, never for a capture already chosen (double press), and again only when the user clicks the dimmed ✦ or « Ask » tile in injected mode (review of bc57857, finding 3): the field then opens if it answers `true`. `menu-key` events are kept by `useTranslation` for their menu capture until the Îlot shows, so a key forwarded before the first render is not lost; so are the keys the WebView itself receives between the activation and the Îlot's first frame (the native agent measured on lot 9 a key sent in the ~25 ms after `focus_overlay` lost twice: the Îlot only shows once its side is read, two IPC answers later): `IlotStage` keeps them from its own first frame (a capture listener, the browser's shortcuts, compositions and lone modifiers aside) and replays them after the forwarded ones through the Îlot's table when it shows, whose own listener starts in that same frame (a layout effect); characters after the one that opened the field become its text; a forwarded key also means the source is in front (injected mode: no field, ✦ dimmed) until a later `focus_overlay` answer, or the overlay window's own `focus` event while the menu waits (a click on the Îlot in the fallback activates it), says otherwise. A keyboard answer is compared with the keys received so far, not with the last render, so a key forwarded just before it does not flip the mode back. A choice calls `choose_action` once, the surface turns into the working pill at once, and a refused choice (French error, announced to assistive technologies) gives the menu back. A `target-invalidated` for the menu capture while no choice is made nor on its way (`choose_action` not answered yet, a double press included) closes the Îlot with `dismiss_overlay`: that menu could only end in a refused paste (review of bc57857, finding 1; the keys typed in the source afterwards are Rust's side). While the Îlot is mounted, the browser's own shortcuts do nothing in it or its field (`preventDefault`, `src/menu/keys.ts` `browserShortcut`: F5 and Ctrl+R with their Shift/Ctrl variants, Ctrl+P, Ctrl+F, Ctrl+G, F3, F7, Ctrl+S/O/U, Ctrl with + = - 0, Alt+← → Home, the keyboard's browser keys), nor does Ctrl + wheel; editing chords and AltGr pass. It complements the WebView's browser accelerators turned off natively (finding 2): a reload would otherwise empty the overlay with its menu scope still open.

## Îlot: shortcut, bindings and triggering (lot 4)

- **Fresh install.** Five English actions, in the order of the grid, each with its letter, short name and Lucide icon: `correct` « Fix grammar » (F, Fix, SpellCheck), `translate` « Translate » (T, Translate, Languages: French → English, anything else → French, one action), `professionalize` « Make professional » (P, Pro, BriefcaseBusiness), `shorten` « Shorten » (S, Shorten, FoldVertical), `email` « Write email » (E, Email, Mail). `menuActionIds` = those five in that order, `defaultActionId` = `correct`, and exactly one binding: `{id:'menu', kind:'menu', shortcut:'Ctrl+Alt+Space', actionId:'correct', outputMode:'replace', enabled:true}`. `src/actionDefaults.ts` mirrors `actions.rs`. The free instruction is not a saved action. A `menuActionIds` the user emptied in the Settings stays empty (validated, never re-migrated): the Îlot then has no action tile and no letter, only « Ask », and its compact state still offers the last action (`src/menu/IlotStage.tsx` `menuActions`; review of bc57857, findings 4 and 6).
- **Under `uiVersion: 'v4'`** a `menu` binding runs `defaultActionId` directly and replaces the selection (its own `actionId` and `outputMode` are ignored); everything else of the 0.4 path is unchanged.
- **Migration of a 0.4 file** (a file without `menuActionIds`, read once then rewritten). Lucas, 24/09: the update must not mix the old and the new (French actions beside English ones, `Ctrl+Alt+T` still showing the result), so what 0.4 shipped and nobody changed gives way to a fresh install's. An action equal to one of the four 0.4 actions (`legacy_defaults`: id, name and instruction as shipped, no letter, short name or icon) is untouched: `correct` and `professionalize` are replaced by the fresh ones of the same id, `translate-fr` and `translate-en` go unless a kept binding runs them or the user chose one as `defaultActionId` (0.4's own default, `translate-fr`, was never a choice). The binding 0.4 shipped, `{id:'primary', kind:'action', shortcut:'Ctrl+Alt+T', actionId:'translate-fr', outputMode:'display', enabled:true}`, goes. Everything the user changed or created stays as it is: nothing of it is renamed, rewritten or dropped. The actions then start with a fresh install's five in the grid's order (a kept action of the same id in its place: a 0.3 `translate` keeps its name and instruction), then the user's others in their order, 24 at most; `defaultActionId` becomes `correct` unless the user chose another. Each grid action gets its letter when free, else the first free letter of its name; actions outside the grid get none; a kept action of a shipped id gets its Lucide icon when it has none (`correct` SpellCheck, `professionalize` BriefcaseBusiness, `translate`, `translate-fr` and `translate-en` Languages), and `professionalize`, only while it is still named « Professionnaliser », the short name « Pro » (review of da-ilot, n°9); `menuActionIds` = the default ids present; the menu binding on Ctrl+Alt+Space is added unless a kept binding (even disabled, any spelling) already uses that chord; `uiVersion` is untouched (a 0.4 file has no `uiVersion`: it reads as the Rust default, `ilot` since jalon B; the browser preview and the e2e fixture start from the Îlot too since lot 14, and ask for `v4` with `ui=v4`). A 0.4 file exactly as shipped therefore reads like a fresh install, its connection and other choices kept. A file older than 0.4 (no `actions`) first gets the four 0.4 actions and its one shortcut on `translate-fr` (kept when its chord is not Ctrl+Alt+T), then the same migration (`actions::migrate_to_ilot`).
- **Last action per application.** At a menu capture Rust reads the source window's executable name (`notepad.exe`, lowercase, never a path or a title) and sets `menu.lastActionId` to the saved action last chosen there, if it still exists (else `null`: the frontend falls back to `defaultActionId`). `choose_action` records a saved action (never a free instruction, never any text) in `menu-memory.json` next to `settings.json`: `{applications: [{process, actionId}]}`, most recent first, 64 applications at most, written through a temporary file then renamed. An unreadable file is an empty memory. The demo (`--demo-selection`) reads no executable name, and neither it nor `--simulate-inference` records anything (review of da-ilot, n°5).
- **Double press.** A second press of the same `menu` binding less than 400 ms after the first (dated when the shortcut event arrives, before any capture work) never captures: while that menu waits, Rust emits `menu-repeat` `{captureId}` to the overlay; if the first capture is still being taken, the event follows as soon as it is stored; if the menu was already chosen or closed, nothing happens. `useTranslation` answers `menu-repeat` itself (so it holds before the menu renders): `choose_action` with `menu.lastActionId ?? defaultActionId`, then `translate` as for any choice. Presses are `MOD_NOREPEAT`: holding the chord does not repeat. The second press chooses while Ctrl+Alt are still held, so `choose_action` gives the foreground back to the source only once the modifiers are up (the overlay keeps it and receives the release, ≤ 1.5 s), and a paste that must reactivate the source waits for the release first: released over the source, Alt would move its focus to its menu bar (Win11 Notepad) and the revalidation would refuse the paste.
- **AltGr.** `shortcut_conflict({shortcut}) -> {altGr: boolean, character?: string}`: for a chord holding Ctrl and Alt on a key that types something (letters, digits, punctuation, Space), Rust asks `ToUnicodeEx` (no keyboard state change) what Ctrl+Alt (+Shift) + that key types on the layout of the foreground window's thread (the settings window while its recorder listens). French AZERTY: `Ctrl+Alt+E` → `{altGr: true, character: '€'}`; `Ctrl+Alt+Space` → `{altGr: false}` (a plain space is not a conflict); a dead key counts. The browser preview answers for French AZERTY. The recorder asks it for every enabled chord holding Ctrl and Alt and shows a warning under it (never a refusal; lot 13).
- **A chord another application holds.** `Ctrl+Alt+Space` may already be registered by another application (`RegisterHotKey` answers `ERROR_HOTKEY_ALREADY_REGISTERED`; measured on the development PC on 2026-09-24, where the chord brought another application to the front): FlowTranslate then cannot register it and reports it at startup like any refused shortcut, opening the settings. The real-window checks of lots 3–4 used `Ctrl+Alt+Shift+Space` in their test settings.

## Îlot: the Settings window (lot 13)

- **Direct links.** Every field an error may point to carries a stable `data-field`: `menuShortcut`, and `quality|fast` + `.endpoint|.apiKey|.model` (`quality.endpoint`…). `SettingsField` (`src/types.ts`) also accepts a bare `endpoint|apiKey|model`, meaning the default profile's (`settings.mode`). The window takes the field from its URL at opening (`?window=settings&field=…`) or from the event `settings-focus-field` `{field}` while open; it opens the Connection details if needed, scrolls to the field, focuses its control and makes it pulse 2.8 s (reduced motion: the same highlight, still). An unknown field is ignored. The frontend calls `open_settings({field})` (`bridge.openSettings(field)`); Rust shows and focuses the window, then emits `settings-focus-field` to it (lot 10, see « Îlot: error codes »).
- **Changes made elsewhere.** The window adopts a `settings-changed` whose content differs from its copy when nothing is pending there (no typing waiting for its 300 ms, no save in flight, no unsaved edit); otherwise its pending edit wins and is saved.
- **Refusals.** Rust's French refusals of a save that the window can meet (shortcut taken, duplicate, letters, grid) are shown in the interface language (`src/settings/messages.ts`) until the error codes of lot 10.

## Îlot: error codes (lot 10)

- **Where.** `code` (`ErrorCode`, snake_case) travels beside the French `message` wherever a failure reaches the frontend as data: `translation` `{kind: 'error', message, code}`, `result-delivery` `{status: 'fallback', message, code}`, `capture-notice` `{message, code}`, `target-invalidated` `{…, code: 'target_changed'}`, and `check_connection` → `{connected: false, message, code}`. The list lives once, `errorCodes` in `src/types.ts` (the type `ErrorCode` is derived from it; `src/result/errors.ts` gives each code its family, its button and its texts): `unreachable`, `timeout`, `unauthorized`, `model_not_found`, `bad_endpoint`, `busy`, `length`, `stream_broken`, `paste_blocked`, `target_changed`, `not_editable`, `too_long`, `cancelled`, `server_error`, `no_selection`, `protected_field`, `keys_held`, `settings_open`, `nothing_recent`, `internal` (Rust's order); a code it does not know reads as `internal`, a notice's included (`useTranslation`). `settings_open` and `nothing_recent` (since the review of da-ilot, see **Capture**) are in the content family, with their own texts. `src/result/errors.test.ts` compares the list with the pairs of `error.rs`'s own serialization test, so a code added on either side fails the tests until both agree. The v4 journey keeps reading `message`. `replace_result` rejects with `{message, code}` (`Refusal`) since the review: `target_changed`, `keys_held`, `not_editable`, `paste_blocked` (`bridge.replaceResult` keeps that object and the Îlot reads its code, `refusalCode`; `bridge.replace` still rejects with the message alone, for the glass of 0.4). Every other rejected command still answers a French string (the 0.4 contract, unchanged so v4 keeps its texts); in the Îlot's journey those rejections are the frontend's own races or mistakes (a stale capture, a second choice, an action that does not match its capture) and read as `internal`: every failure that asks something of the user arrives as one of the events above.
- **Server** (`inference.rs`). Nothing at the address (refused, unknown host, TLS, no connection within 5 s) → `unreachable`; its message names the cause with the host alone (0.5.1, `inference::cause`, read from Windows' own codes under reqwest's error: a certificate Windows refuses, another TLS failure, a name that does not resolve, nothing listening, no route, a connection that never opened in time or was cut). TLS goes through schannel (reqwest `native-tls`): the certificates Windows trusts are trusted, a company's authority or a firewall's TLS inspection included; Windows' proxy settings are not read; a server that accepted then stayed silent past 120 s, before or during the stream → `timeout`. Statuses (`error::http_status`): 401 and 403 → `unauthorized`; 404 whose body mentions « model » (vLLM « The model … does not exist », OpenAI `model_not_found`, Ollama) → `model_not_found`; any other 404, and a 3xx (redirects are never followed: the address is wrong) → `bad_endpoint`; 429 and 503 → `busy`; any other status (400, 500, 502…) → `server_error`. An address the settings refuse (`validate_endpoint`) → `bad_endpoint`. The stream: `finish_reason: length` → `length` (never pasted); any other reason than `stop` → `server_error`, and the reason is no longer part of the message (it is the server's word); unreadable UTF-8 or JSON, an event cut in the middle, no `stop` or no `[DONE]`, a body cut short → `stream_broken`; a complete answer with nothing in it (a thinking block alone) → `server_error`. Cancelled, or overtaken by a newer request → `cancelled` (the pill just leaves). An HTTP client that cannot be built, a display that fails → `internal`. `check_connection` classifies the same way on `/v1/models`: any 404 there is `bad_endpoint`, an answer that is not a model list is `bad_endpoint`, a model the list lacks is `model_not_found`.
- **The server's body** only classifies (a retry without the extra sampling fields, a 404), inside `inference.rs`: never in a message, an event, a log or a test output.
- **Capture** (`capture-notice`). Nothing selected (no UIA selection, no copy) → `no_selection`; the Settings window in front → `settings_open`; a password field, or a field UIA cannot tell apart → `protected_field`; over 6,000 characters → `too_long`; the source window changed during the capture → `target_changed`; the tray's « Revoir » with nothing recent → `nothing_recent` (the last two since the review of da-ilot; before, both were `no_selection`). The frontend reads the code only, never the message.
- **Paste** (`result-delivery` fallback). Another application in front, the field, the element or the selection changed (collapsed to the caret included) → `target_changed`; the watcher had already dropped the selection → `target_changed`; a capture that never had a writable selection (a console, a password field, a copy the user made himself, a replay) → `not_editable`; the shortcut's keys still held after 600 ms → `keys_held`; a NUL in the result, the clipboard busy, the chord blocked, a source that cannot be brought back to the front → `paste_blocked`.
- **Tests.** Every code is produced in the Rust tests by a fake OpenAI server (127.0.0.1, a port of the test's own, raw HTTP answers) or a simulated case: `inference.rs` (statuses, stream, transport, cancellation, `check`), `capture.rs` (capture and paste refusals), `error.rs` (the snake_case list), `lib.rs` (a result without target, the shortcut states).
- **A link to a field.** `open_settings({field?})` shows and focuses the settings window, then emits `settings-focus-field` `{field}` to it. Accepted: `menuShortcut`, `endpoint|apiKey|model` (the default profile's) and `quality.|fast.` + those; any other value only opens the window. The window is created hidden at startup: a link sent in the very first instant, before its page listens, only opens it.
- **The state of each shortcut.** `shortcut_status() -> ShortcutStatus[]`, one per binding in the settings order: `{bindingId, shortcut, state}` with `registered`, `taken` (Windows answered ERROR_HOTKEY_ALREADY_REGISTERED: another application holds the chord, the case of `Ctrl+Alt+Space` measured on 2026-09-24), `failed` (any other refusal) or `disabled`. Event `shortcut-status` (the same array) to the settings window once the startup registrations are done and after every save. A save tries the refused chords that are still wanted again (the other application may have let go) and never fails because of them; a new chord that is taken still refuses the save as before (« Le raccourci est déjà utilisé ou indisponible. »).
- **The Settings window shows it** (front, `src/settings/registrations.ts`): it asks `shortcut_status()` as it opens and takes every `shortcut-status` after that (an event newer than the command's answer wins). Under the menu row and on each direct shortcut's card, an enabled binding whose chord is `taken` says, in English or French, that another application already uses it so Windows did not give it to FlowTranslate, and to record another combination or close that application; `failed` says Windows refused it. A warning, never a lock: the recorder stays free (the line steps aside while it listens), and a state only counts while the binding still names the chord Windows answered for, so a chord just recorded waits for the next `shortcut-status`. `disabled` and `registered` say nothing. The browser preview reports every enabled chord as registered; the IPC fixture can set any state (`shortcutStates`, `&shortcutTaken=<binding>`) and sends `shortcut-status` after each save, as Rust does. Under the menu row, a `taken` chord also gets a proposal (Lucas, 24/09: the default chord already taken at the first launch): the front asks `suggest_shortcut()` whenever the chord or its state changes and offers « Use <chord> », saved in one click by the usual path; none free, the warning alone. The browser preview proposes Ctrl+Alt+Shift+Space; the fixture answers what `suggestion(value)` set.
- **Restore default settings** (Lucas, 24/09). `reset_settings() -> Settings`: Rust saves `settings::reset` of the current settings by the path of `save_settings` (the shortcut registered, `shortcut-status` and `settings-changed` sent) and empties the Îlot's last action per application (`menu-memory.json`). When Windows refuses the default menu chord (another application holds Ctrl+Alt+Space, Claude desktop on Lucas's PC), the menu keeps the enabled chord it had and everything else is restored (`settings::keep_menu_chord`); the row then says so. Back to a fresh install: actions, bindings, grid, default action, appearance, result bubble, after replacing, `uiVersion` and the hidden switches. Kept, as they set this device up: `profiles` and `mode` (the connection), `connectionExpanded`, `historyEnabled`, `autostart` and `language`. The answer carries the API keys to the settings window only. The last row of « On this device » asks once more in place (« Keep my settings », focused, or « Restore default settings »; Escape keeps them), then the window adopts the answer; an edit still waiting gives way, and is saved when Rust refuses the reset. `src/settings/reset.ts` mirrors `settings::reset` for the browser preview and the fixture.

## Îlot: the lines of the selection (lot 5)

- **`Capture.selectionRects`** (absent when empty): the lines of a UI Automation selection, in **physical screen pixels** like `anchor` (the unit of `GetBoundingRectangles` under Per-Monitor V2), top to bottom then left to right. They are data for Rust's own placement: the frontend never positions anything from them. Whatever draws on them converts once, for its own window: `selection_lines::halo_frame(lines, scale, margin)` grows their union by `margin` logical pixels onto whole physical pixels (the window) and gives each line in logical pixels relative to that window's top-left corner, at the window's DPI scale (unit-tested at 100, 150 and 200 %, on screens at, right of and left of the origin).
- **From runs to lines** (`selection_lines::lines`): UIA gives one rectangle per visible run (several per line when the style changes, none for a line scrolled out of view). Runs that are not finite or have no area are dropped; the others are clipped to the source window (`GetWindowRect`) and dropped when nothing of them lies inside it. Runs overlapping vertically over half the shorter one form a line; within a line, runs merge unless a gap wider than the line height separates them (two table columns stay two segments). Beyond 64 segments, counted per line (review of da-ilot, n°8): the segments of the first line, one box for the lines in between (held between the first line's bottom and the last line's top), and the segments of the last line; a first or last line of 32 segments or more is one box. The rectangles never overlap, columns included.
- **Unchanged:** `anchor` stays the raw last rectangle UIA gives (none when that one is unusable), physical; the placement and `validate_target` compare it exactly as before. The synthetic copy, a copy the user made, a replay and an application without usable rectangles (VS Code's Monaco has no TextPattern) give no `selectionRects`: no effect on the text, the pill alone. `--demo-selection` carries two fixed lines ending on its anchor.

## Îlot: the halo window (lot 6, « mise en valeur »)

- **Window.** `halo` (`/?window=halo`, created hidden at startup, `focusable: false`): transparent, no shadow, no material. `WS_EX_TRANSPARENT | WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` are set once at startup (with Tauri's `set_ignore_cursor_events(true)`) and re-applied at each placement; it publishes no surface, so the 8 ms hit tester never touches it and it never takes a click or the focus. It counts as one of our windows (a press over it never captures it) and receives `settings-changed` (theme, motion).
- **When.** Under `uiVersion: 'ilot'` only, for a capture that still has its anchor and `selectionRects`. A UI Automation capture also keeps two more levels (`capture::selection_levels`): the text box (the focused element's bounding rectangle, clipped to the source window) and the whole lines the selection touches (its first and last lines expanded to `Line`, merged per line), and the colour of the ground under the text (`ground.rs`: a few pixels just outside the lines, read once at the capture, before any of our windows covers them, in one `BitBlt`; the colour at least two of them agree on, else the one inside the text box's corners; no pixel is stored or logged, the colour only travels as the three numbers of the event). A menu capture shows `phase: 'menu'` once the overlay is placed; `translate` shows `phase: 'work'`. - **Until.** The menu's halo stays until the work replaces it. The response (`done` or `error` of the current request) sends `phase: 'leave'`: the page fades out in 150 ms and the window hides 200 ms later. It hides at once (`phase: 'clear'`) on a dismissal, a new capture, `cancel_translation` of the running request, and the context watcher's invalidation (source window moved or left, selection changed, scrolled or collapsed: `validate_target` compares the anchor, and a readable control that no longer holds a selection, after a click or an arrow key, counts as a change, so neither the halo nor a paste outlives it: before, such a paste inserted the result at the caret). While the halo is visible the watcher checks every 105 ms instead of 420 ms. A generation orders the calls: a stale leave or hide never touches a newer run, and the page ignores older generations.
- **Page** (`src/halo/`, the values of Lucas's choice in `design-lab/mise-en-valeur.html`). `menu`: the text box's line (inset 3 px, radius 9, `0 0 0 1px` at .6 and `0 0 0 4px` at .12 of `--hl`), a band per whole line (padded 3 × 1 px, radius 4, `--hl` at .08, .07 on a dark ground) and the tint of the exact text (padded 1 px, radius 3, `--hl` at .24, .28 dark), still, shown at once. `work`: the bands stay, the box's line becomes the aurora (a conic ring violet, pink, amber turning in 4.5 s over its glow blurred 9 px at .7) and the tint becomes the reflection on the letters (a band of the ground's own colour at .8 over a faint violet wash, 1.8 s a pass, `cubic-bezier(.45,0,.55,1)`, computed on the strip of the runs laid end to end, so it runs from the end of one line into the start of the next). The colours follow `data-tone` (the ground), else the app's `data-theme`; on a light ground the iris hues are deeper (Lucas found the pastels too pale on white). Under `data-motion="reduced"` everything holds still: a fixed iridescent veil (.24, .27 dark) instead of the reflection, a still ring, no wave. `html[data-halo-ready]` marks the listener as installed.
- **Marks (lot 9, « mise en valeur »).** The same window draws the changed words of a replacement (`phase: 'marks'`, see « the result »), placed on the words and the new text + 16 px: a wave of light over the new text's lines (`whole`, once, 1 s, `cubic-bezier(.4,0,.2,1)`), then the iridescent glow on the words (padded 2 px, radius 4, one gradient across the marks, violet to amber at .30 with a 12 px glow at .32 on a light ground, pastels at .26 and .22 on a dark one) rising from 380 ms over 420 ms (260 ms without `whole`), held, 900 ms out at `leave`.
- **Test switch.** `FLOWTRANSLATE_SIMULATE_WORD_MS` (1 to 2000, simulated inference only): the delay between simulated words (65 ms by default), so the real-window checks can watch the halo while the work lasts.
- **Naming.** Unrelated to the shadow margin called `halo` in `src/layout.ts` and `glass.css` (the transparent room around the glass inside the overlay window).

## Îlot: the result (lot 9)

- **After the paste.** Under `uiVersion: 'ilot'`, once the automatic paste succeeded, Rust finds the pasted text with UI Automation, still under the state lock (no capture commits in between): the range that ends at the caret (the end of the first selection range, so a paste that leaves its text selected works too) and spans the result's length in the provider's characters. Providers count UTF-16 units or code points and write a line break as CR, LF or CR LF: a few candidate lengths are tried and the one whose text reads back as the result (line endings and non-breaking spaces aside) is kept; three tries over about 200 ms. `result-delivery` `{status: 'applied'}` then carries `pastedRects` (the new text's lines, physical, grouped and clipped like `selectionRects`; absent when the text was not found) and `undoable` (found, and `afterReplace.undo` on). Under v4: no `pastedRects`, `undoable: false`. The texts (original, result, provider's copy) stay in Rust's memory for the comparisons: nothing emits, logs or stores them.
- **The pill's place.** `result_pill({requestId, width, height}) -> PillTarget` for a pill of that size (logical): its top-left corner relative to the overlay window as it stands, logical (negative, or beyond the window, when it does not fit there). `side: 'below'` (default): 8 px under the last line of the new text, its right edge on the end of that line, clamped into the work area; no room below: `above` the first line, its right edge still on the end of the line the text ends on; `pillPlacement: 'margin'`: right of the widest line, centred on the last one, tried first (no room on the right: below, then above). Never over a line of the new text: `clear: false` only when no candidate fits the screen (then below, clamped). `estimated: true` when the pasted text was not found: the old selection's lines grown or shrunk by the ratio of the lengths, ending on the old anchor moved by that many lines. `inside: true`: the pill fits in the window there (within half a pixel), the frontend may move its surface in the DOM (no `SetWindowPos`); `inside: false`: `move_overlay` first, then ask again. Refused for a stale request.
- **Moving the window.** `move_overlay({captureId, dx, dy})`: moves the anchored overlay window by (dx, dy) logical pixels and resolves once placed; the surfaces are relative to the window and move with it. Rust never moves the window by itself while the pill animates: the frontend calls it at a moment its surface rests (the check drawn, or the surface faded), then `result_pill` answers relative to the moved window. Every later placement of the capture keeps the shift (`resize_overlay`); a drag replaces it (the manual place), the next capture resets it. Refused for a bottom or unanchored form, a stale capture, a drag in progress, or a move larger than the work area.
- **Changed words.** `highlight_changes({requestId, ranges: TextRange[]}) -> HighlightResult`: `ranges` of the result in UTF-16 code units (JavaScript string offsets, `src/result/highlight.ts`), end excluded, at most 64 (« whole block » is one range from its first to its last visible character). Rust aligns them with the provider's text (CR LF against LF, non-breaking spaces), resolves each as a sub-range of the pasted text, checks its text, and draws its lines (a range's runs merge per line, two ranges never do; 256 lines at most) in the `halo` window, `phase: 'marks'`. Answers `{ranges, lines}`: how many ranges were found, how many lines are drawn (0: nothing shown, also when the pasted text could not be found). The marks, Undo offered or not (Lucas, 25/09): a wave over the new text, then held until the user's next action in the text, `afterReplace.changedWordsSeconds` at most (60 s by default, 5 to 120): a key down that is not ours (`dwExtraInfo = 0x464C5754`) and not a lone modifier or lock key, Escape included (the keyboard hook); a button pressed or the wheel turned anywhere but on our pill (a low-level mouse hook on its own thread, installed only while the marks show, `host::arm_marks_watch`); then 900 ms out, ease-out, the window hidden 950 ms after. Neither the pill's countdown, nor the withdrawal of Undo, nor the overlay's dismissal ends them (`halo::dismiss` keeps them). Undo, the text moving, scrolling or reflowing, another window in front and the next capture hide them at once. Under reduced animations, no animation.
- **Undo.** `undo_result({requestId}) -> UndoOutcome`, once per replacement. `undoStrategy: 'keystroke'` (default): Ctrl+Z to the source; `'repaste'`: the pasted text is selected (UIA `Select`), read back (Chromium applies the selection a moment later: up to 400 ms), and the original pasted over it through `capture::paste` (the clipboard kept as for any paste). Both: the source is brought back first when one of our windows holds the foreground (refused when another application does), then rule 1 after that reactivation: the same window, the same focused control, the same UIA element (runtime id), the pasted text still exactly right before the caret; the keys released (600 ms at most, else `keys_held`); all checked again. After Ctrl+Z, the original must read back (selected, or right before the caret) within 800 ms: `undone` with `confirmed: true`; a field that cannot be read: `undone`, `confirmed: false`; read and not back: `failed`, `paste_blocked`. `refused` means nothing was sent: `target_changed` (the text, the caret, the field or the window changed, or Undo was already withdrawn), `keys_held`, `paste_blocked` (the source cannot be brought back, the chord blocked before any key). The marks hide at once.
- **Undo withdrawn.** Event `undo-state` `{requestId, available: false, reason}` to the overlay, once: `typed`, a key went down in the source window (any key but the modifiers, the lock keys and Escape; another tool's injected keys count; our own keys carry `dwExtraInfo = 0x464C5754` and never do); `undo_key`, the user's own Ctrl+Z in the source (it passes through: the application undoes the paste itself); `caret_moved`, the watcher no longer finds the pasted text right before the caret (a click elsewhere, a selection, another field). The marks end with it for their own reason (the key, the caret leaving the text), not because of Undo. It may reach the page before `result-delivery`. The frontend removes Undo and reads the reason (front, below): `undo_key` → « Undone », then the Îlot leaves; `typed`, `caret_moved` → the check alone, which leaves within 1.1 s.
- **Watcher after the paste.** While a replacement is current the context watcher checks every 105 ms. The caret after the pasted text (the selection the paste collapsed) is normal and keeps pill and marks. The source window moving or resizing, another application in front, or the pasted text's rectangles moving by more than a pixel (a scroll, a reflow) dismiss: `overlay-dismiss-requested`, halo hidden at once, even while its marks fade; the caret no longer after the text withdraws Undo and fades the marks. One of our windows in front (a click on the pill) changes nothing. After the dismissal the marks keep their own watch (`watch_marks`, every 105 ms, while they show): the window moved, another application in front or the text's rectangles moved hide them; the caret leaving the text fades them.
- **Tests.** Rust: the candidate lengths, the alignment, the provider's character index and an Undo refused without its source in front (`pasted.rs`), the pill's place and the estimate (`placement.rs`), the keys that end Undo and the keys, clicks and wheel that end the marks (`host.rs`), the ground's points, agreement and luminance (`ground.rs`), a dismissal that lets a fading halo end its fade, the marks that outlive the overlay and the frame of the three levels with its tone (`halo.rs`), the scene of a capture, the last line, a scrolled text and the shapes of the events (`lib.rs`), the bounds of `changedWordsSeconds` (`settings.rs`). Playwright: every phase with its values and its reduced form, the tone from the ground or the theme (`e2e/halo.pw.ts`). Real windows: Notepad and a Chrome `textarea` (reports of the lot, lengths and booleans only); Word and Outlook: manual recipe in docs/RECETTE.md.

  - **transient** (`timeout`, `busy`, `server_error`, `stream_broken`, `length`, `internal`, and any code the front does not know): Try again runs `translate` again for the same capture, action and mode (`useTranslation.start`, the v4 relaunch), once per failed request, and the surface goes back to the working pill.   - **content** (`too_long`, `no_selection`, `protected_field`): the text and ✕ only.

## The real glass (0.6)

What floats (the Îlot, the pills, the bubble, the setup window) really blurs what is behind it. Research and choices: docs/VERRE-0.6.md (with « Ce qui a été construit » at its end); the trial of 0.5 it replaces: docs/ACRYLIC-TRIAL.md.

- **Setting.** `settings.glassMaterial: 'glass' | 'painted'`, `'glass'` by default. A file of 0.5.1 or older gets `'glass'` whatever it says (the trial's `painted` was never chosen); `'acrylic'` reads as `'glass'`. `'painted'` keeps the painted material everywhere. Not shown in the Settings window yet.
- **Native side** (`src-tauri/src/backdrop.rs`). No second window: each window that carries glass (`overlay`, `setup`) gets a `Windows.UI.Composition` visual tree on its own HWND (`DesktopWindowTarget`, not topmost: under the transparent WebView), with `DWMWA_USE_HOSTBACKDROPBRUSH`. One visual per surface: Windows' host backdrop brush (already blurred by the shell, never read by the app) clipped by a rounded rectangle of any place, size and radius. The glass belongs to the window: it moves and hides with it and cannot outlive it.
- **Command.** `glass_frame(seq: u64, scale: f64, shapes: GlassShape[]) -> bool`, `GlassShape = { x, y, width, height, radius, opacity }` in CSS pixels of the window (`scale`: `devicePixelRatio`), `seq` ordering the messages of a page (a late one is dropped). Rust mirrors the list (8 shapes at most, every value clamped, `backdrop::panes`), and answers whether the real glass shows. Only `overlay` and `setup` are served.
- **Page side** (`src/glassBackdrop.ts`, started by `App.tsx` in the native overlay and setup). On every frame (after Motion's writes) it measures the glass surfaces (`overlayGlassSurfaces`: the selector list of the `data-backdrop="glass"` rule of `src/theme.css`; `.su-window` in the setup) as painted: box after transforms, corner radius, opacity through the ancestors. A shape is sent one frame after it was measured and only as far as the next frame still covers it (`overlap`), so the blur never shows outside the surface. Unchanged shapes are sent again every 250 ms. No per-animation message: entrance, morph, slide, fade, exit and interruptions all go the same way.
- **Attribute.** The page sets `data-backdrop="glass"` on `<html>` when `glass_frame` answers true (tint, grain, rim and shadow stay the page's), removes it otherwise (`opaque` in the setup): the painted material is the CSS default, so a silent Rust side never leaves a hole.
- **Fallback.** Painted when: build below 22000 (Windows 10), a remote session, high contrast, « Effets de transparence » off, energy saver, `glassMaterial: painted`, or any native error (then until the next start, one `glass.unavailable` line in the journal with Windows' error code). Conditions are read again at most every 500 ms while a surface shows: switching transparency off or on changes the material live. **Test switch.** `FLOWTRANSLATE_ACRYLIC_FALLBACK=windows10|remote|contrast|transparency|energy` forces one condition.
- **Windows.** Glass windows have Windows' own opening animation off (`DWMWA_TRANSITIONS_FORCEDISABLED`). The setup window is created hidden, cloaked (`backdrop::veil`), shown, and uncloaked at its page's first surface (1.5 s at most): no white rectangle, no empty frame.
- **Tests.** `backdrop.rs` unit tests (the decision, the injection, the clamping, the blur's opacity); `src/glassBackdrop.test.ts` (selector list in step with the stylesheet, radius, overlap); real-window checks in docs/VERRE-0.6.md.

## Commands

- `get_settings() -> Settings`
- `frontend_ready() -> Capture|null`: overlay-only handshake, called after event listeners register. Marks overlay ready and returns pending capture, if any. Frontend deduplicates capture IDs. Never recapture clipboard as a startup fallback. A second call while a capture is on screen means the overlay page loaded again under it (a reload, a crash): Rust closes that capture as `dismiss_overlay` would (scope closed, nothing pasted, the window hidden about 300 ms later) and answers `null` (review of da-ilot, front n°2).
- Browser accelerators: the overlay, halo and settings WebViews are created with `AreBrowserAcceleratorKeysEnabled` off (set through `ICoreWebView2Settings3` right after each window is built, `browser_keys.rs`): F5, Ctrl+R, Ctrl+P, Ctrl+F, F3, Ctrl+Plus/Minus and the browser keys do nothing in our pages; copy, paste, undo, select all and the arrows stay. Measured on 2026-09-24 in the real window: with the Îlot focused, F5 and Ctrl+R reloaded the overlay page 3 times out of 3 without the setting, 0 out of 5 with it.
- `save_settings({settings}) -> void` (validate URL/model/shortcut before saving; DPAPI-protect credentials)
- `capture_text() -> Capture` (also usable from preview/test controls). Since 0.4.0 `canReplace` is decided at capture (`capture::replaceable`): true for an editable UIA selection or a successful synthetic copy, false for the user's own fresh copy, a replay, a demo, a console window or a password field; no second step. Without a UIA selection Rust copies for the user (synthetic Ctrl+Insert after the shortcut chord is released, clipboard sequence watched ≤ 350 ms, previous text restored without feeding Win+V unless something else wrote in between), else accepts a copy the user made himself less than 3 s before (`host::track_clipboard`), else fails with « Rien à traduire dans la fenêtre active. » shown as a notice, never as a MessageBox.
- `translate({request:{id,captureId,text,mode,actionId}}) -> void`: starts background streaming and returns promptly. Emits `translation` StreamEvent. Register listeners before invoking. At most one active request; starting another cancels the prior one. Validate capture/text identity. Desktop demo may be explicitly started through CLI `--demo`, never silently substitute a mock for failed inference.
- `cancel_translation({requestId}) -> void`
- `copy_result({requestId}) -> void`: Rust copies only a completed known translation, never arbitrary frontend-supplied replacement text.
- `replace_result({requestId}) -> void`: menu « Remplacer »; revalidates the stored target, reactivates the source window and pastes once (`capture::paste`); the target is consumed even on refusal, the error string is shown as feedback. Since the review of da-ilot it rejects with `{message, code}` (`Refusal`): a result no longer current or the paste blocked `paste_blocked`, a capture that can no longer be replaced or another application in front `target_changed`, then the paste's own codes (`target_changed`, `keys_held`, `not_editable`, `paste_blocked`).
- `dismiss_overlay() -> void`: cancel immediately and emit `overlay-dismiss-requested` with `{captureId}`. Native fallback hides after 300ms. When the overlay holds the foreground (Îlot menu), the source gets it back first.
- `choose_action({captureId,actionId,instruction?}) -> ExecutionInfo`: Îlot menu choice, once per menu capture (see the Îlot section).
- `demo_menu_capture() -> Capture` (lot 14, probe only): opens the Îlot menu on the demo selection as a `menu` binding's press would, for `npm run ui:native` (scripts/probe-native-ui.mjs). Honoured only from the overlay, in a `--demo…` process started under the WebView2 probe (`FLOWTRANSLATE_CDP_URL`), under `uiVersion: 'ilot'`; the capture has no source window (0), so the hook never takes a key from the application in front. `src-tauri/src/demo_menu.rs`.
- `shortcut_conflict({shortcut}) -> ShortcutConflict`: whether the chord is also AltGr + a key on the active layout (see the Îlot section, lot 4).
- `complete_overlay_dismiss({captureId}) -> void`: acknowledge the closing animation; stale acknowledgements do nothing.
- `open_settings({field?}) -> void`: shows the settings window; with `field` (a `SettingsField`, lot 13) Rust then emits `settings-focus-field` to it (lot 10).
- `shortcut_status() -> ShortcutStatus[]`: whether each binding's chord is registered, taken by another application, failed or disabled (lot 10).
- `suggest_shortcut() -> string | null` (Lucas, 24/09): a chord for the menu that Windows gives now, the first of Ctrl+Alt+Shift+Space, Alt+Shift+Space and Ctrl+Alt+Home that no enabled binding uses and that types no AltGr character with the layout in front (registered, then released at once); never Ctrl+Shift+Space, Word's non-breaking space. null when none is free.
- `reset_settings() -> Settings` (Lucas, 24/09): « Restore default settings », see the Îlot section.
- `result_pill({requestId,width,height}) -> PillTarget`: where the pill goes after a paste under the Îlot (lot 9, see « the result »).
- `move_overlay({captureId,dx,dy}) -> void`: moves the anchored overlay window by logical pixels, at a moment the frontend chooses (lot 9).
- `highlight_changes({requestId,ranges}) -> HighlightResult`: the changed words in the halo after Rust's own paste, until the user's next action in the text (lot 9, « mise en valeur »). `clear_highlight` was removed on 25/09: the front no longer ends them.
- `undo_result({requestId}) -> UndoOutcome`: Undo of the replacement, once, after revalidation (lot 9).
- `system_theme() -> {dark: boolean}|null` (lot 1): the Windows app mode (`HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`), for the setting « Theme: follow Windows »; null when the value is missing, and the front then keeps `prefers-color-scheme`. Event `system-theme` `{dark}` when the mode flips (`RegNotifyChangeKeyValue`). Needed because the app's WebView2 answers `prefers-color-scheme: light` whatever Windows says (measured on 2026-09-24: tauri-runtime-wry creates the WebView with an explicit light theme when tao does not detect dark mode).
- `system_motion() -> {reduced: boolean}|null` (lot 2 of docs/DA-PLAN.md): whether Windows asks to reduce animations (« Effets d'animation », `SPI_GETCLIENTAREAANIMATION`), for the setting « Animations : suivre Windows »; null when Windows does not answer, and the front then keeps `prefers-reduced-motion`. Read in Rust because nobody has measured whether WebView2 passes that switch on to the media query (it does not pass the app mode on to `prefers-color-scheme`, lot 1).
- `focus_overlay() -> boolean`: the Îlot menu's keyboard (see the Îlot section). Waits until the overlay is shown, brings it to the foreground (`SetForegroundWindow`), repairs the frameless style and answers whether the overlay really holds the foreground afterwards. Overlay and halo visibility never goes through Tao's `show()`/`hide()`: Tao 0.35 rebuilds the styles with `WS_CAPTION` on its deferred visibility diff, which DWM paints as a title.
- `start_drag({clientX,clientY}) -> void`: only overlay; starts native movement after a primary pointer press on non-interactive content. Coordinates are logical client pixels captured on pointerdown; Rust validates them and compensates pointer travel before IPC delivery, then uses native dragging while the button remains pressed. Retain the manual location across streaming/menu resizes until the next capture. Buttons and scrollbars keep their own interactions.
- `resize_overlay({width,height,captureId?,presentation?,regions?,frame?}) -> void`: logical pixels. Since 2026-09-14 the ceiling is the work area of the screen the window rests on (physical against logical, no more 640×800): a larger window is refused with « Dimensions invalides. ». The bounds include the shadow halo (32 px each side, 20 px above, 44 px below anchored, 16 px below the bottom band) and are **reserved** once per capture (`src/layout.ts`): anchored, 444 × max(measured glass, 334) so the wait pill, the short glass and the menu under its pill only change the regions; bottom, `bottomReserve(screen, preset)` (band width + 64, by top halo + 236 px menu reserve above the pill + pill band + tallest band + 16) with the root projected on the window's bottom edge. `frame` is the glass footprint Rust anchors and clamps into the work area: while waiting, the 380 × one-line footprint of the glass to come, so the pill alone already sits where the glass opens; afterwards region zero. Regions are unchanged (one to six tight rounded surfaces, hit-test only: the window carries no Win32 region, Chromium paints the silhouette with per-pixel alpha and `host::start_hit_tester` polls the cursor every 8 ms to toggle `WS_EX_TRANSPARENT | WS_EX_LAYERED`). Rust applies the rectangle (`host::place`) only when it changed and the surfaces (`host::set_regions`) whenever they changed: a regions-only update costs no `SetWindowPos`. A work area shorter than the reserve truncates the bottom window from the top and Rust shifts the regions accordingly; anchored, only the glass is clamped, the transparent reserve may leave the work area. Stale capture IDs do nothing.
- `presentation: 'anchored' | 'bottom'` (2026-09-14, replaces contextual/reader/docked): the form is decided once, on the settled result, and never switches afterwards (no « Agrandir », no tab, no fold). `anchored`: the short glass (≤ 8 lines at 380 px) opens from its wait pill beside the selection, keeps its chosen side and its drag position. `bottom`: the reader band (half the work area wide, at most 45 % of its height, whole lines, scrollable beyond) rests bottom-centre of the **cursor's** screen (`host::monitor_at(None)` at the switch, `manual` reset), bottom edge anchored, and follows the cursor across screens (see `work-area`). Clipboard and unanchored captures open bottom.
- `overlay_dimming({dimming}) -> void`: the reading budget is spent and the frontend starts the two-step exit (55 % in 600 ms, held 1.4 s, 300 ms fade) → Rust closes the Escape scope so Escape belongs to the user again; `dimming: false` (an approach, a wheel or a key restored the glass for 5 s) re-arms it while the window is visible. Then `dismiss_overlay` / `complete_overlay_dismiss` as before. Budget (`src/layout.ts`, `readingBudget`): orientation (1 s anchored, 1.5 s band) + 350 ms per word, between 5 s and 30 s (short) or 90 s (band), scaled by `autoClose`; a pointer visit of at least one second followed by a departure shortens what remains to 4 s, never below 2.5 s; a click, wheel or key restores the whole budget; the pill's pin (band only) suspends it.
- `drag_settings() -> void`: settings window only; starts the native move from the home-made title bar.
- `quit_app() -> void`: exits the application (settings footer).
- `check_connection({mode}) -> ConnectionStatus` (with `code` when not connected, lot 10). It checks the saved profile: the Settings save an edit still waiting (300 ms) or not confirmed first, and check nothing when that save is refused (« Not checked: this change couldn’t be saved », 0.5.1)
- `get_history() -> HistoryEntry[]`
- `delete_history({id: string|null}) -> void`: null deletes all.

## Events and windows

- `halo` carries `HaloEvent` to the halo window only (lot 6, see above); older generations are ignored.
- `menu-repeat` carries `MenuRepeat` to the overlay: the double press of the menu shortcut (lot 4); `useTranslation` runs the last action of that application; stale capture ids are ignored.
- `menu-key` carries `MenuKey` to the overlay: a menu key the native hook took from the source while the Îlot menu waits and the overlay never held the foreground for it, or while its capture was still being taken (held, then emitted after `capture`); stale capture ids are ignored.
- `capture-target` carries `{captureId, canReplace}`: since 0.4.0 only `canReplace: false`, once a paste consumed the target (automatic or from the menu); a stale capture id is ignored.
- `result-delivery` carries `ResultDelivery` after the automatic paste of a « replace » capture (see above); under the Îlot, `pastedRects` and `undoable` (lot 9).
- `capture-notice` carries `{message}`: nothing to translate, protected field, oversized selection, source window changed. Without an open glass Rust first places the overlay window as a pill alone (420×64 logical, bottom centre of the cursor's screen, no surface: the mouse passes through) and hides it after 4 s; with an open glass the frontend shows the message as feedback. Replaces the MessageBox (2026-09-14).
- A `capture` with `replay` (tray « Revoir la dernière traduction », kept 10 min after the glass closed) is shown complete by the frontend without invoking `translate`; `copy_result` accepts its request id.
- `work-area` carries `Screen` (logical work area and scale) to the overlay when the cursor moved to another screen while a bottom form is visible: the hit tester reports `MonitorFromPoint(cursor)` on change, `screen_changed` moves the window to the new screen (`placement::docked` on its work area) and the frontend recomputes the band width and republishes its geometry. An anchored glass belongs to its selection and never follows. `capture.screen` carries the same values for the first computation. No cursor position is emitted.
- `capture` carries Capture to overlay, after it is ready; every capture starts translation at once in React (the clipboard confirmation step was removed on 2026-09-10). The global shortcut always captures the current selection, clipboard fallback included; it no longer focuses an existing glass.
- `translation` carries StreamEvent. React ignores stale request IDs. Rust emits done only on normal, non-truncated completion.
- `settings-changed` carries Settings after successful persistence.
- `settings-focus-field` carries `SettingsFocus` to the settings window: scroll to that field, focus it, highlight it (lot 13; sent by `open_settings({field})` since lot 10).
- `shortcut-status` carries `ShortcutStatus[]` to the settings window after the startup registrations and after every save (lot 10).
- `undo-state` carries `UndoState` to the overlay when Undo is no longer safe: a key in the source, the user's own Ctrl+Z, the pasted text no longer before the caret (lot 9).
- `system-motion` carries `{reduced: boolean}` to every window when « Effets d'animation » flips: a hidden top-level window of the `system-motion` thread re-reads `SPI_GETCLIENTAREAANIMATION` on each `WM_SETTINGCHANGE` and emits only a change.
- `target-invalidated` carries `{captureId:string,anchorLost:boolean,message:string,code:'target_changed'}` (code since lot 10): ignore stale capture IDs; disable replacement and native window moves to bottom only when anchorLost. Never sent for a menu still waiting for its choice: that menu closes instead (see « Leaving the menu »). Under `uiVersion: 'ilot'` the window keeps its place, anchor and side (the working pill, then the error pill, stay where the user looks) and `anchorLost` is `false`; under `v4` the glass loses its anchor and docks at the bottom (`anchorLost` true when it had one). A capture is invalidated once, and only when two watcher checks in a row, 35 ms apart, see its target lost (window moved, another application in front, selection changed); a null foreground is never another application. Right after a capture the foreground passes to the Îlot (`focus_overlay`), and a single check during that handover could read no foreground, or UI Automation already answering for our window: that closed about 2 % of menu captures in Chrome within 40 ms of their `capture` event (measured on 2026-09-24, before the confirmation). Should one still arrive for a menu capture with no choice made nor on its way, the frontend closes that menu itself (Îlot section, Frontend).
- `overlay-dismiss-requested` carries `{captureId:string}`. Frontend completes its exit animation then acknowledges it; a new capture invalidates the old request and timeout.
- `glass-near` carries `{near:boolean}` to the overlay, emitted by the hit tester on change only: whether the real cursor rests within 32 logical px of one of the published regions (the silhouette and its shadow, never the whole reserved window). The frontend holds the glass open while `near` is true and starts its 500 ms fold once it turns false; a click grants two seconds regardless. No cursor position is ever logged or emitted.
- Window labels: `overlay` loads `/?window=overlay`, `halo` loads `/?window=halo`, `settings` loads `/?window=settings`.
- Only overlay subscribes to capture/translation and starts requests. Settings and halo may subscribe to settings-changed (the halo also to `halo`), never trigger translation from global capture events.
- The capsule window, no longer shown since 2026-09-10, was removed with lot 6 (docs/DA-PLAN.md §4.2): its entry in `tauri.conf.json` and the capabilities, its Rust placement and Escape scope, the `Capsule` component, its styles, messages and lab scenario. Its tests were rewritten for the halo; `focus_overlay` stays (the Îlot menu).
- Frontend publishes no IPC command capable of executing a shell, opening arbitrary files, or injecting arbitrary keystrokes.
- Showing/resizing never activates the overlay; only `focus_overlay` does, for the Îlot menu, and after a choice the overlay cannot be activated at all until the next capture. Escape is captured by a scoped native hook only while overlay is open if the source retains focus; while the Îlot menu is open the hook takes only the menu keys, and only when the source kept the foreground because the overlay never got it. No unrelated keys are intercepted, and no key is ever logged.
- Glass calibration since 2026-09-14: one graphite `rgba(24,26,31,.96)` for glass, pill and menu, a 1 px 20 % edge, no sheen; copy `#e8eaef`, letter-spacing 0, `text-wrap: pretty`, sizes from the `textSize` preset (`--copy-size`/`--copy-line`). The packaged window paints **no native material**: `DWMWA_SYSTEMBACKDROP_TYPE` (Tauri `Effect::Acrylic`) is drawn behind the entire window bounds regardless of the window region (the grey frame Lucas reported) and any material shows through DOM fades. `FLOWTRANSLATE_GLASS=blur|acrylic|dwm` re-enables a material for experiments (`host::apply_glass`). The browser preview keeps its own `backdrop-filter`. Text stays fully opaque. Shadows live in the halo (`--glass-shadow: 0 12px 32px rgba(0,0,0,.34)`, glass.css sizes the halo to it); the halo never blocks a click since the hit-test reads the tight regions.
- Rust preserves the chosen above/below side during a stream; the deltas are buffered in `useTranslation` (2026-09-10) and, since 2026-09-14, the wait is a pill alone (60×28, shadcn's spinner: lucide `LoaderCircle` 18 px turning once a second, a sweep after 1.5 s) at the upper-right of the glass to come; the settled text is measured off-screen at 380 px (`measureLines`) and the form is decided once: ≤ 8 lines → short glass unfolded from the pill (`clip-path`), more → reader band. Since 0.2.1 (UI-025) the placement itself is decided at the capture on the source text (`decidePlacement`: anchored and ≤ 8 lines → beside the selection, else bottom), so a long selection waits at the bottom from the start and the band is born there; only a short source translated long still moves to the bottom invisibly before the band rises 8 px in 220 ms. When the switch to `bottom` lands on another screen than the selection's, Rust emits `work-area` at once. `start_drag` is only invoked after 4 px of pointer travel; Rust still compensates the travel since the press. When geometry is genuinely lost, re-anchor to bottom explicitly.

## 0.6: servers, connection check, journal, setup (docs/PLAN-0.6.md)

Types in `src/types.ts`, wrappers in `src/bridge.ts`, preview in `src/bridge.mock.ts` (`?conn=<scenario>`). Rust sends codes, never sentences.

- **Settings.** `servers: Server[]` (1 to 8; `{ id, name, endpoint, apiKey, noKey, model }`), `defaultServerId`, `setupDone`, `changedWordsStyle` (`encre` | `eclat`). `mode`, `profiles`, `connectionExpanded` are gone. `endpoint` is stored without `/v1`; `save_settings` normalises it (`settings::sanitize`), trims the model and drops the key of a `noKey` server, then validates (an address that does not read, a default server that does not exist, more than 8 servers are refused). An empty address or model is valid: a request then fails as `bad_endpoint` / `model_not_found`. Keys reach the `settings` and `setup` windows only.
- **Migration.** A file of 0.5.1 or older (no `servers`) is turned into servers once (`quality` then `fast`, when set up and different; factory profiles are not servers), `setupDone` true when at least one server came out of it; the old file stays as `settings.0.5.bak.json`.
- **Requests.** `TranslationRequest.serverId`, `ExecutionInfo.serverId` (the default server at the capture; the first request must name it), `Replay.serverId`, `HistoryEntry.server` (a host, empty for older rows). `SettingsField` is `menuShortcut`, a bare `endpoint | apiKey | model` (default server) or `<serverId>.<field>`.
- **Events are per window.** `bridge.on` hears what Rust emits to the window's own label and what it emits to everyone, nothing else (Tauri's plain `listen` hears every window's events: keys would reach the overlay, and the keyless copy the Settings).
- **`probe_connection(run, endpoint, apiKey, noKey) → ProbeResult`** (`settings`, `setup`): checks what is typed. Steps `address → reach → key → models`, each change as `probe-step { run, steps }` to the calling window, one journal line per step. A new check from the same window cancels the older one (`problem.cause: 'cancelled'`); `cancel_probe(run)` too. Limits: name 5 s, connection 5 s, `GET /v1/models` 10 s. A server that connects and never answers fails the `reach` row (`reach.timeout`). `reach.certificate` (Windows refused the certificate) is distinct from `reach.tls`. Through a proxy of the environment (`HTTPS_PROXY`…), name and connection are judged by the request itself; a local server is never proxied.
- **`list_models(serverId) → ModelInfo[]`** (rejects with a `ProbeProblem`), **`try_model(run, endpoint, apiKey, noKey, model) → TryResult`** (one fixed synthetic sentence, 30 s, reply of 200 characters at most, never logged), **`check_connection(serverId?)`** (the check of 0.5 over the probe, until the old Settings page goes).
- **Journal.** `get_diagnostics() → DiagEntry[]` (500 last, oldest first), `clear_diagnostics()`, event `diagnostic`. Also written to `logs/diagnostic.log` (local data folder, or `<FLOWTRANSLATE_DATA_DIR>/logs`), rotated at 1 MB. Real requests write a `request` line. Never a text, a body or a whole key (`••••3f2a`).
- **Windows.** `open_setup(replay?)`, `finish_setup(openSettings)`, `open_demo()`, `close_demo(done)` (event `demo-ended { done }` to `setup`; the demo also ends when its window is closed, and after 60 s), `open_settings(field?, page?)` (event `settings-focus-field { field?, page? }`). The setup opens at launch while `setupDone` is false, except with `--demo*`, `--settings` or `FLOWTRANSLATE_SKIP_SETUP=1`. The setup page finds `data-backdrop="glass" | "opaque"` on `<html>`. A shortcut pressed over the Settings, the setup or the demo is refused (`settings_open`).
- **Test hook.** With `FLOWTRANSLATE_CDP_URL=http://127.0.0.1:<port>` every window is inspectable over the DevTools protocol on that port (WebView2 ignores `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` once the app gives its own arguments).
- **Clipboard.** A user's fresh copy marked `ExcludeClipboardContentFromMonitorProcessing`, or `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard` = 0, is never taken as the source.

## 0.6: robustness (field test of 0.5.1, Lucas 01/10)

- **Two error codes.** `read_only` (family `paste`: the paste went out and nothing changed, a PDF in a browser; the result exists, « Copy result ») and `protected_window` (family `content`: the window in front runs as administrator; a capture notice, and a refusal of the paste).
- **One gesture, one bubble.** A press of a shortcut is ignored (nothing queued, nothing opened) when it follows the previous press within 500 ms (the window slides: twenty presses are one gesture), when a bubble opened or its work started less than 1.2 s ago, or while a capture is still being taken (given up after 10 s). The double press of lot 4 (under 400 ms, `menu-repeat`) is told apart first. For 700 ms after a choice (slid by each key, 3 s at most) the plain keys typed in the source are dropped by the keyboard hook: Enter mashed after the shortcut never types over the selection. Never our own keys, a chord with Ctrl/Alt/Win, a modifier, or Escape.
- **No state stays.** Escape closes the bubble in front of any window (seen by the hook at its press; left to the application in front unless it is the source or the bubble). A watchdog (every 500 ms, its own thread, `try_lock`) ends what outlived its limit without a sign of life: menu 120 s and pill 60 s (never while the pointer is on them) → dismissed; working 150 s, or 30 s once the target is lost → the request is cancelled and `translation { kind: 'error', code: 'timeout' }` is emitted (a closable error pill); a delivery that never reports 20 s, a dismissal the page never acknowledged 2 s, the window shown over nothing 8 s, the state lock held 20 s → the emergency exit. The emergency exit (also the tray's « Fermer la bulle », id `close`) hides the window by its handle at once, forgets the state and reloads the overlay page.
- **Journal, step `app`** (states only, never a text, a title or a path): `shortcut.captured` (detail `menu|direct · uia|copy|fresh|… · replaceable|read only`, ms), `shortcut.refused` (cause: the error code; detail: the check that gave up, `no clipboard change`, `copied nothing readable`…), `shortcut.ignored` (detail `rapid|burst|capturing|own window`, one line a second at most), `shortcut.repeat`, `target.lost` (detail `window moved|window switched|text|length|anchor|collapsed|element|control|window`), `paste.done` (detail `read back|assumed · undo offered|no undo`), `paste.refused` (cause + detail), `undo.done|refused|failed`, `watchdog.timeout`, `watchdog.dismissed` (detail: the state), `bubble.closed` (cause `tray` or the watchdog's reason; detail: what was on screen).
- **Clipboard.** After a synthetic copy the kept clipboard is put back within the same clipboard session as the read, once the counter rested (Scintilla and OLE write in several steps); after our paste, the proof is the ownership of the clipboard, not its counter; a copy that lands after the wait is undone if the session saw no input since. A copy the user makes meanwhile is never overwritten.
